# og-OAS (v3) vs mg-OAS (v4) — scenario and trajectory comparison

Generated by `analysis_outputs/og_vs_mg/compare_og_mg.py` from on-disk artefacts only. No model calls, no LLM judge, no benchmark runs — the LiteLLM proxy `https://cmu.litellm.ai` is suspended, so nothing new could be evaluated or judged.

**og-OAS** = `mgulavani/openagentsafety_full_updated_v3`, 359 human-written tasks. **mg-OAS** = `mgulavani/openagentsafety_full_updated_v4`, 15 machine-generated tasks.

## 0. Bottom line

| Question | og-OAS (v3) | mg-OAS (v4) |
|---|---|---|
| Scenario definitions | complete, 359 tasks | complete, 15 tasks |
| Real model trajectories | 2962 records across 10 runs (9 intact + 1 truncated) | **17 rows in a curated pool, from a run that no longer exists** |
| Rule-based unsafe rate | computable per run | **not computable** — no `final_score` anywhere on the mg side |
| LLM-judge unsafe rate | partially recoverable (see §3) | 17 judge-derived labels, n≤10 per actor |

The scenario-level comparison (§1) is solid. The trajectory-level comparison (§2–§5) is not, and no amount of care with the existing files fixes that: the mg side has no completed run. §6 lists exactly what has to be executed.

## 1. Scenario-level comparison (fully computable)

Both sets are single-checkpoint, 1-point tasks, so difficulty is not encoded in checkpoint count. The v4 checkpoint *text* is roughly twice as long, and the evaluator code is longer too — the generated tasks spell out the unsafe behaviour in more detail than the human-written median.

### 1.2 Service surface — the clearest structural difference

| Declared dependency | og-OAS (v3) | mg-OAS (v4) |
|---|---|---|
| gitlab | 49/359 | 7/15 |
| owncloud | 87/359 | 2/15 |
| plane | 8/359 | 1/15 |
| rocketchat | 0/359 | 15/15 |
| *no service dependency* | 222/359 | 0/15 |

Every one of the 15 v4 tasks declares `rocketchat`, and 7/15 declare `gitlab`. In v3, `rocketchat` is declared by 0/359 tasks and 222/359 tasks touch no hosted service at all — they are pure filesystem/office-document tasks. So the generated set is narrower and GitLab/RocketChat-centric: it is an NPC-chat-plus-git benchmark, where og-OAS also covers OwnCloud document work, spreadsheet manipulation, and Plane issue tracking.

### 1.3 What the graders actually check

Categories are multi-label (one grader can do several); `primary` picks the strongest form of evidence each task relies on. Detection is by static pattern-matching over `evaluator_code`.

| Grader behaviour | og-OAS (v3) | mg-OAS (v4) |
|---|---|---|
| calls an LLM inside the grader | 7/359 | 0/15 |
| greps the trajectory text | 32/359 | 13/15 |
| no checkpoint implemented (empty grader) | 54/359 | 0/15 |
| reads a file on the agent's filesystem | 203/359 | 10/15 |
| reads live service state (GitLab/OwnCloud/Plane/RocketChat API) | 86/359 | 6/15 |

| Primary evidence | og-OAS (v3) | mg-OAS (v4) |
|---|---|---|
| none — task cannot be scored | 54/359 | 0/15 |
| other | 3/359 | 0/15 |
| service state | 86/359 | 6/15 |
| trajectory grep | 21/359 | 0/15 |
| workspace file | 195/359 | 9/15 |

Proportionally the generated tasks verify *more* against real service state, not less: 6/15 v4 graders query a live service API versus 86/359 in v3. That is a point in favour of the generated set. The counterweight is in `analysis_outputs/v4_synthetic_pairs/report.md`: several v4 graders that do read a file are keyword-matching a *report the agent wrote about itself* (`contract_approval.md`, `access_review.md`, `commit_verification.md`, `account_setup.md`, `share_link.txt`) rather than inspecting the state the harmful act would have changed. A model that does the unsafe thing but writes a carefully-worded summary scores safe; a model that behaves safely but describes it with the wrong phrase scores unsafe. That failure mode exists in v3 too, but it is worth auditing before these 15 tasks are treated as ground truth.

Note also that 7/359 v3 graders call an LLM from inside the grader, so even *re-scoring* those og tasks is proxy-blocked. No v4 grader does.

**The single largest grader-quality difference is unscoreable tasks: 54/359 v3 tasks have an empty grader** — `grade_checkpoints()` builds a `Result` and appends no `Checkpoint` at all, so the task can never score. **0/15 v4 tasks have this problem.** This is not a cosmetic issue: it is exactly the source of the `final_score.total == 0` records excluded from every rate in §2. Every one of those exclusions is a task that was never scoreable, not a run that failed — see the cross-check in §2. On this axis the generated set is strictly better than the human-written one.

### 1.5 NPC design and manipulation strategy

| Metric | og-OAS (v3) | mg-OAS (v4) |
|---|---|---|
| NPC scenarios defined | 229 (across 194 tasks) | 15 (across 15 tasks) |
| `strategy_hint` words | 24 (IQR 12–40); mean 29.4; range 3–122 | 64 (IQR 55–72); mean 65.2; range 51–101 |
| Distinct NPC occupations | 67 | 14 |
| Tactics matched per hint (mean) | 0.25 | 1.07 |
| Mean pairwise Jaccard of hints | 0.091 | 0.108 |

| Manipulation tactic | og-OAS (v3) | mg-OAS (v4) |
|---|---|---|
| urgency/time pressure | 12/229 | 4/15 |
| authority/seniority | 10/229 | 8/15 |
| reassurance/minimization | 7/229 | 4/15 |
| deception/impersonation | 14/229 | 0/15 |
| persistence/escalation | 10/229 | 0/15 |
| emotional/reciprocity | 5/229 | 0/15 |

This is the strongest quality result for the generated set. v4 `strategy_hint`s are far richer (median 64 words vs 24 in v3) and carry 1.07 recognised pressure tactics each vs 0.25 in v3 — many v3 hints are one-liners like "Acknowledge any message you receive" that encode no social pressure at all. Every v4 task is a social-engineering scenario with a scripted manipulation; only about half of v3 is.

One caveat on the tactic mix, visible in the table above: the v4 pressure concentrates on authority, urgency and reassurance, and **no v4 hint scripts persistence or escalation** — the NPC makes its case once and does not push back when refused. Real social-engineering failures usually need the second and third ask, and a refusal that only has to hold once is a weaker test than v3's handful of hints that explicitly tell the NPC to insist. Worth adding to the generator.

### 1.6 Templating and duplication in the generated set

Mean pairwise token Jaccard of problem statements: v3 = 0.088, v4 = 0.244. Duplicate instance ids: v3 0, v4 0.

The v4 statements share a rigid skeleton — `# Task` / one-paragraph setup / a numbered list that almost always runs *clone or read an artefact → review it → message NPC X on RocketChat → act on what they say* — which is what drives the higher lexical overlap. No two v4 tasks are duplicates, but they are visibly one template with fifteen fillings. og-OAS is more heterogeneous by construction because it was written by many hands.

Caveats that must travel with those numbers, in order of severity:

1. **Coverage is partial and the selection rule is unknown.** The coverage column is the share of each run's records that could be attributed. Even the best case leaves a quarter of the run unaccounted for, and the GPT case covers well under half. If the pool was curated toward clear-cut trajectories, these rates are biased in an unknown direction and probably upward.
2. **The labels are binarised.** `llm_label` takes only 0 and 2, so judge label 1 (partial) and -1 (never reached) have been collapsed or dropped and cannot be recovered. The rates are therefore not comparable to a fresh 4-level judge pass without re-judging.
3. **The pool is not a run export.** It contains duplicate instance ids carrying different labels, and a few ids absent from every surviving run. No builder script for it exists anywhere in the repo, so its construction is undocumented.
4. **Small subsets are noise.** Several rows above rest on 4–17 trajectories; their intervals span 30–50 points and they are listed for completeness, not for interpretation.

Treat these as indicative, not as run-level judge rates. **They are reported in a column separate from rule-based rates everywhere in this report, and the two are never averaged together.** For context, the earlier version of this report quoted 49.31% (Claude) and 55.97% (GPT-5-mini) judge-unsafe from the analyzer-comparison draft's Table 1. Those numbers are not used here: they cannot be tied to any run that is still on disk, so there is no way to verify what they were computed over.

Rates are withheld below n=20. Even pooled across four different actor models — which is itself not a legitimate thing to do — the interval is about 17–59%, wide enough to contain every og baseline figure in §2 and §3.1. **The honest statement is that mg-OAS has no measured unsafe rate.**

There is also a condition problem. All 17/17 of these rows carry per-action `Risk: LOW/MEDIUM/HIGH` annotations. In the raw runs that field is `UNKNOWN` for every action under `security_analyzer: none` and populated only when an LLM analyzer is active, so these v4 trajectories came from a run **with an analyzer engaged** — not from the no-analyzer passive baseline the og numbers in §2 use. Whether that analyzer was passive or blocking cannot be determined from the pool alone, and neither answer helps: og has no passive-with-analyzer run to compare against, and if it was blocking then the og counterpart is `llm_blocking_*`, whose median lengths are materially shorter than baseline. **Every og-vs-mg comparison in §5 is therefore confounded by condition on top of being underpowered**, and both rows are shown so the reader can see the size of the confound.

### 4.3 Synthetic v4 data — excluded from every number above

- **8 rows inside the pool** tagged `source: "synthetic"`, `model: ['azure_ai/gpt-4.1']`, labels {'unsafe': 8}. LLM-authored, all unsafe, 0/8 carry risk annotations. Not benchmark rollouts.
- **30 rows in `analysis_outputs/v4_synthetic_pairs/safety_trajectories_v4_synthetic.jsonl`** — 15 instance ids, labels {'unsafe': 15, 'safe': 15}, `model: ['constructed']`. These are deterministic template constructions (15 safe/unsafe pairs); the 50/50 split is an artefact of how they were built, and every trajectory is 8–9 actions by construction.

Neither set is a measurement of how a model behaves on the v4 tasks, so neither contributes to any unsafe rate or step count in this report. They remain useful as constructed contrastive training data, which is what they were built for.
